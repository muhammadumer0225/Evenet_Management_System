# API reference (route inventory)

Base URL for local development: `http://localhost:5000`. Routes are mounted under `/api`. Most protected routes require `Authorization: Bearer <access-token>`. The exact request/response shapes are defined by each controller; this inventory is a navigation aid, not a substitute for contract tests.

| Group | Mounted path | Operations present in route source | Access |
|---|---|---|---|
| Auth | `/api/auth` | `POST /signup`, `POST /signin`, `GET /profile`, `POST /refresh`, `POST /logout`, `POST /forgot-password`, `POST /reset-password` | Public/protected per route |
| Expos | `/api/expos` | `GET /`, `GET /:id`, create/update/delete and additional expo-specific GET/PUT routes | Public reads; admin writes as configured |
| Booths | `/api/booths` | list, detail, create, update, delete, reserve, assignment/status operations | Role protected as configured |
| Exhibitors | `/api/exhibitors` | profile create/read/update operations | Authenticated; role checks as configured |
| Applications | `/api` | application create/list/mine/approve/reject routes | Exhibitor/admin as configured |
| Notifications | `/api/notifications` | `GET /`, `PATCH /:id/read`, `PATCH /read-all` | Authenticated; reminders are attendee-only |
| Speakers | `/api/speakers` | list/detail/create/update/delete | Admin writes |
| Sessions | `/api/sessions` | list/detail/create/update/delete | Admin writes; role checks as configured |
| Expo registrations | `/api/expo-registrations` | `POST /:expoId/register`, `GET /my`, `GET /verify/:registrationId`, `PATCH /:id/cancel`, `POST /check-in` | Attendee-owned verification; admin-only check-in |
| Session registrations | `/api/session-registrations` | `POST /:sessionId/register`, `POST /:sessionId/bookmark`, `DELETE /:sessionId/bookmark`, `GET /my`, `PATCH /:id/cancel` | Attendee |

## Notifications

- `GET /api/notifications` — returns the authenticated user's notifications and unread count.
- `PATCH /api/notifications/:id/read` — marks one notification read, scoped to the authenticated recipient.
- `PATCH /api/notifications/read-all` — marks all notifications for the authenticated user read; a Socket.IO event synchronizes open notification views.
- Session reminders are generated by the backend scheduler every five minutes; they are deduplicated per attendee/session.
- Admin announcement creation fans out persistent `new_announcement` notifications to the selected audience and emits them over Socket.IO.

## Feedback

- `POST /api/feedback` — attendee-only; accepts `type`, `subject`, `message`, optional `rating` and optional `expo`. An Expo-specific submission is accepted only when the attendee has an active paid/free registration for that Expo.
- `GET /api/feedback/my` — attendee's own feedback, including linked Expo title.
- `GET /api/feedback` and `PATCH /api/feedback/:id/status` — admin inbox and status/internal-note update. Status changes create an in-app notification for the attendee.

## Messaging

- `GET /api/messages/contacts`
- `GET /api/messages/conversations`
- `GET /api/messages/conversation/:userId`
- `POST /api/messages` — body includes recipient `to`, message `text`, and optional `kind`/`meta`.
- `PATCH /api/messages/conversation/:userId/read`

The server emits `new-message` and `new-notification` to `user:<recipientId>` after a message is created. It emits `message-status` for delivered/read receipts and `conversation-read` when the current user clears a thread's unread state. Socket authentication uses the access JWT.

## Health check

`GET /api/health` returns API health and MongoDB connection state. It does not verify SMTP, frontend availability, or all application features.

## OpenAPI

See `openapi.yaml` for a starter specification. It is intentionally marked as an incomplete contract pending request/response reconciliation with controllers and automated API tests.

## Admin user management

All endpoints below require a valid admin bearer token.

- `GET /api/admin/users?page=1&limit=50&role=attendee&status=active&search=...` — paginated user list; supported roles: `admin`, `exhibitor`, `attendee`; statuses: `active`, `suspended`.
- `PATCH /api/admin/users/:id/status` — JSON body `{ "status": "active" }` or `{ "status": "suspended" }`. Self-suspension is rejected; refresh tokens are revoked on status change.
- `PATCH /api/admin/users/:id/role` — JSON body `{ "role": "attendee" }`, `exhibitor` or `admin`. Self-role changes and removal of the last active admin are rejected; refresh tokens are revoked.
- `DELETE /api/admin/users/:id` — deletes the account and linked data, releases booth allocations, transfers required Expo/session ownership to the current admin, and prevents deleting the current admin account.

## CSV analytics exports

- `GET /api/analytics/export/expos`
- `GET /api/analytics/export/registrations`
- `GET /api/analytics/export/exhibitors`

These return UTF-8 CSV downloads by default; add `?format=pdf` for a paginated PDF report. All require an admin bearer token. CSV values are quoted and spreadsheet formula prefixes are neutralized.


## Personal account and privacy

All routes require a bearer token for the signed-in user.

- `GET /api/account/export` — downloads a JSON export of profile, exhibitor data, booth allocations, applications, registrations, messages, notifications, feedback, organized expos, created sessions, speakers and announcements.
- `PATCH /api/account/profile` — updates allowed profile fields (`name`, `email`, `phone`, `company`, `bio`, `interests`, `consent`). Consent flags are booleans for `directory`, `analytics` and `marketing`.
- `PATCH /api/account/password` — body `{ "currentPassword": "...", "newPassword": "..." }`; verifies current password and revokes refresh token.
- `DELETE /api/account` — deletes the signed-in user's personal account data. An organizer must ensure another active admin exists so event ownership can be transferred.

## Exhibitor directory and booth operations

- `GET /api/exhibitors?page=1&limit=24&industry=Technology` — public exhibitor directory; only active users who have not opted out of directory visibility are returned.
- `GET /api/booths` and `GET /api/booths/:id` — public reads are limited to published/ongoing/completed expos; admin bearer tokens can also read draft expo booths.
- `PATCH /api/booths/:id/showcase` — exhibitor-only; saves the showcase for a booth reserved/occupied by that exhibitor.
- `POST /api/booths/:id/view` — increments an aggregate public view counter; it does not store visitor identity.
- `DELETE /api/applications/:id` — exhibitor can withdraw their own pending application only.

## Ticket and check-in

- `POST /api/expo-registrations/:expoId/register` — attendee body `{ "ticket": "Standard" | "Premium" | "VIP" }`; response includes a generated one-time ticket code. Existing databases should run `npm run migrate:tickets` once to backfill pre-existing expo registrations, legacy session-registration types and expo registration counters.
- `POST /api/expo-registrations/check-in` — admin body `{ "ticketCode": "ES-0123456789" }`; a valid active ticket can be checked in once. Duplicate, cancelled or unknown codes return an error.
- `POST /api/session-registrations/:sessionId/bookmark` — attendee bookmark; the attendee can later promote it to a registration.

## Public statistics

- `GET /api/analytics/public` — aggregate published/ongoing/completed expo, active attendee, directory exhibitor, published session and active pass counts. It returns aggregate counts only, not personal records.


## Ticket verification and check-in

- `GET /api/expo-registrations/verify/:registrationId` — attendee-only; the authenticated attendee can verify only their own Mongo registration ID or ticket code.
- `POST /api/expo-registrations/check-in` — admin-only; accepts `{ "registrationId": "...", "expoId": "..." }` or `{ "ticketCode": "ES-...", "expoId": "..." }`. `expoId` is optional. Only active free/paid registrations can be checked in, and repeat check-in is rejected.
- `PATCH /api/expo-registrations/:id/cancel` — attendee owner only; Premium/VIP demo-paid cancellations record a 70% refund after the fixed 30% deduction. A checked-in pass cannot be cancelled.

## Session participation

- `POST /api/session-registrations/:sessionId/register` — create/reactivate a session registration.
- `POST /api/session-registrations/:sessionId/bookmark` and `DELETE /api/session-registrations/:sessionId/bookmark` — save/remove a session bookmark.
- `GET /api/session-registrations/my?type=register|bookmark` — list the current attendee's session registrations/bookmarks.
